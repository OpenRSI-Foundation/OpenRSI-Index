| Research Question | Scientific question | Under a fixed BrowseComp-Plus offline-document environment and matched training and inference budgets, can submission-level hill climbing over competence-conditioned curriculum policies—where every submission starts from the same frozen QUEST-4B checkpoint, performs exactly one verifiable proposer–solver LoRA SFT self-play round, and is evaluated before the next submission—produce a solver whose single-rollout accuracy exceeds that of the unchanged checkpoint on the Judge-hidden, access-controlled official 130-question QUEST workload, without adding original QUEST training examples, reinforcement learning, or an external training teacher? |
| Research Question | Why this is scientific research rather than pure engineering optimization | The hypothesis is that training a deep-research proposer on grounded tasks solved in exactly one or two of three independent solver rollouts will identify a useful competence boundary, while training the solver only on fully verified successful trajectories will convert that curriculum into transferable retrieval and reasoning gains.<br><br>QUEST’s [`generate_tasks.py`](https://github.com/OSU-NLP-Group/QUEST/blob/962e10b6b99f53efc8fd45229ed80728b9ee9a05/task/obj_task/generate_tasks.py), [`generation_agent.py`](https://github.com/OSU-NLP-Group/QUEST/blob/962e10b6b99f53efc8fd45229ed80728b9ee9a05/task/obj_task/generation_agent.py), and [`generation_prompts.py`](https://github.com/OSU-NLP-Group/QUEST/blob/962e10b6b99f53efc8fd45229ed80728b9ee9a05/task/obj_task/generation_prompts.py) generate tasks from preset categories and complexity settings. Its [`curriculum_sampler.py`](https://github.com/OSU-NLP-Group/QUEST/blob/962e10b6b99f53efc8fd45229ed80728b9ee9a05/training_scripts/rl/recipe/deepresearch/curriculum_sampler.py) adapts sampling among existing tasks rather than training a proposer to construct new tasks around current solver competence. Recent systems such as [SearchMaster](https://arxiv.org/abs/2608.01822), [Skill Self-Play](https://arxiv.org/abs/2607.22529), [Socratic-SWE](https://arxiv.org/abs/2606.07412), and [Self-Optimizing Multi-Agent Systems for Deep Research](https://arxiv.org/abs/2604.02988) make adaptive self-generated supervision timely, while the proposed SFT-only, independently rolled out, executable-verifier mechanism remains a distinct test.<br><br>Each submission starts from the same frozen `P0` and `S0`, runs one generate–solve–select–update round, and produces one `S1`. Judge then returns aggregate feedback before another submission can start. The three adaptive submissions use those aggregate results to hill-climb in curriculum-policy space: a better-scoring adaptive policy becomes the incumbent; after a non-improving step, the next adaptive attempt returns to the incumbent before applying a new bounded change. Model weights, optimizer state, tasks, trajectories, and replay data never cross submission boundaries. Two fixed controls—fixed proposer and no competence filter—remain unchanged, so the study can distinguish policy improvement from generic additional SFT or hidden-set continuation training. |

| Evaluation | Fixed evaluation protocol | **One-round Work self-play.** Every submission starts from the same frozen base, `P0`, and `S0` and completes exactly one self-play round before hidden evaluation. `P0` produces exactly 256 raw task outputs, with recorded model search calls using the same offline top-5, 512-token-snippet interface as the solver. Each proposer acts as a full deep-research agent: it searches and reads multiple documents, selects hash-anchored evidence, synthesizes a grounded multi-hop public question, and emits a task-specific verifier program and record. Every raw output consumes one slot and is never replaced. Candidate-controlled Work code may additionally read and analyze the pinned local corpus and index directly for curriculum and task construction, within the fixed hardware, wall-clock, provenance, output, rollout, and training budgets.<br><br>A valid task must state every checked requirement in its visible question, cite at least two distinct pinned-corpus documents, attach the relevant evidence records and hash-anchored spans, and pass the fixed meta-verifier. The proposer-generated verifier receives only the solver response and attached evidence and returns normalized deterministic JSON containing a partial-completion score and full-pass result; no LLM judge participates. Every verifier execution occurs as an unprivileged process in an ephemeral, digest-pinned Python 3.11 sandbox with the original fixed standard-library/SDK, no-network, filesystem, CPU, RAM, process, runtime, output, privilege, and system-call limits. The evaluator runs it twice under a sanitized deterministic environment and requires identical normalized output. The fixed meta-verifier rejects malformed, nondeterministic, response-independent, constant-pass, constant-fail, evidence-unsupported, question-inconsistent, or undeclared-input verifiers and independently validates cited evidence against the pinned corpus.<br><br>Each meta-valid task receives exactly three independent `S0` rollouts with fixed independent seeds and no shared state, answers, verifier feedback, or revision history. Verification occurs only after all three finish. Tasks at 0/3 or 3/3 are consumed but excluded from ordinary competence-boundary solver training; only 1/3 and 2/3 tasks are retained. Retained proposer research trajectories become proposer SFT data. Only fully verified solver trajectories from retained tasks become solver SFT targets; partial and incorrect responses are excluded. Invalid proposer outputs receive no solver rollout and unused slots are not reassigned. Thus each submission has exactly 256 raw proposer outputs and at most 768 solver rollouts. Proposer and solver keep the original fixed Work inference caps, stochastic settings, and disabled external memory summarization.<br><br>Train `P1` from `P0` and `S1` from `S0` exactly once. Both use the pinned QUEST/LLaMA-Factory BF16 LoRA stack: rank 64, alpha 128, dropout 0.05, the original declared target modules, frozen base weights, `qwen3_5` template, 32,768-token window, and global batch eight. Each role update runs 32 optimizer steps and exactly 1,048,576 loss-bearing role-generated tokens using deterministic packing and resampling from eligible traces, for 2,097,152 loss-bearing tokens across the two updates. AdamW retains the declared learning rate `1e-4`, betas, epsilon, zero weight decay, gradient clipping, warmup, cosine schedule, and evaluator-owned seeds. Optimizer and scheduler state initialize once and end with the submission. Proposer loss covers only proposer-generated tokens; solver loss covers only solver-generated reasoning/action tokens, search queries, tool calls, and final answers. Environment-provided content remains masked. Candidate and baseline use the same question order, one evaluator-owned seed per question, retrieval assets, Qwen3-Embedding-8B FAISS top-five retrieval, 512-token snippets, temperature, presence penalty, output-token cap, timeout, prompts, Luna route, and GPU class. Each adaptive successor must cite prior aggregate feedback, identify the highest-scoring valid adaptive policy as the incumbent, and declare one bounded curriculum-policy change.
